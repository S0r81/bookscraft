# UUIDv7 identifiers and scoped external references

## Context and Problem Statement

Rows move between desktop and server, and between export and import. Imports must be idempotent (I-7). A QBO `Id` is unique only within one company and one entity type (G-3). Contacts can be both customer and vendor (G-4). Document numbers repeat in real data (G-7).

## Decision Drivers

* Stable ids across files and machines.
* Re-runnable imports.
* Faithful import of messy source data.

## Considered Options

* UUIDv7 ids; `external_ref` unique on `(source, realm, external_type, external_id)`; contacts with role flags; non-unique document numbers
* Integer autoincrement ids
* External ids as columns on each table
* One `kind` per contact

## Decision Outcome

Chosen option:

* **UUIDv7** generated by the application (`IdGen` port): sortable by time, globally unique.
* **`external_ref`** rows scope every source id by source, realm (QBO realmId, or the file hash for IIF and CSV) and source entity type. They keep the source's SyncToken and raw payload.
* Bank lines are deduplicated by `(account, FITID)`, or by a content hash plus ordinal.
* **Contacts carry role flags** (customer, vendor, employee).
* **Document numbers are not unique.** The UI warns on duplicates.

### Consequences

* Good, because imports are idempotent and lossless, and files can be merged or moved without id clashes.
* Bad, because UUIDs in TEXT take more space than integers. That is acceptable at small-business scale.

### Confirmation

UNIQUE constraints in schema.sql; T-MIG-1 (double import), T-BANK-1 (re-import).

## Pros and Cons of the Options

### UUIDv7 + external_ref

* Good, because ids are portable and imports idempotent.

### Integer ids

* Bad, because they collide across files and leak counts.

### External id columns per table

* Bad, because a row can come from several sources over time.

### One kind per contact

* Bad, because agencies often buy from and sell to the same party.
