# Data model

Status: accepted (2026-10-10). Owner: `storage-engineer`. Normative DDL: [`schema.sql`](schema.sql) (company file) and [`schema-system.sql`](schema-system.sql) (system file). Posting semantics: [LEDGER_SPEC.md](LEDGER_SPEC.md).

## 1. Conventions

| Kind | Storage | Rust type (crate `domain` or `money`) |
|---|---|---|
| Identifier | `TEXT` UUIDv7, lowercase, 36 chars; generated by the application | `XxxId(Uuid)` newtype per entity |
| Civil date | `TEXT 'YYYY-MM-DD'`, `CHECK (date(x) IS x)` | `domain::Date` (wraps `jiff::civil::Date`) |
| Timestamp | `TEXT 'YYYY-MM-DDTHH:MM:SS.sssZ'` (UTC, milliseconds) | `domain::Timestamp` (wraps `jiff::Timestamp`) |
| Money | `INTEGER` minor units in the row's currency; postings are +debit / −credit | `money::Minor(i64)`, `money::Money { minor, currency }` |
| Currency | `TEXT` ISO 4217, upper case | `money::Currency` |
| Decimal (qty, unit price, rates, percents) | `TEXT` canonical decimal: optional `-`, digits, optional fraction, no exponent; never `REAL` or `NUMERIC` | `rust_decimal::Decimal`, written with `normalize()` |
| Boolean | `INTEGER` 0/1 with CHECK | `bool` |
| JSON | `TEXT` with `json_valid()` CHECK | typed struct via `serde` |
| Optimistic concurrency | `version INTEGER` on every row the API changes by id (lists, documents, bank lines, bank rules, bank feeds, reconciliations, import runs, the company), +1 per update; the unversioned resources (no `version`, no `If-Match`) are listed in API.md §2 | ETag `W/"<version>"` at the API (API.md §2) |
| Error codes from triggers | `RAISE(ABORT, '<namespace>.<code>')` | `store::StoreError::Constraint(ErrorCode)` mapped 1:1 to API error codes |

Every table is `STRICT`. Foreign keys are enforced (`PRAGMA foreign_keys = ON` on every connection).

## 2. Files

| File | Contains | Location (platform crate, `directories`) | Holder |
|---|---|---|---|
| Company file `*.bookscraft` | All accounting data of one company, its audit log and its attachments | Default `<data_dir>/companies/`; any local path the user picks | One process at a time (exclusive lock) |
| System file `system.bookscraft` | Users, memberships, sessions, API tokens, company registry, job queue, server secrets, system audit log | `<data_dir>/` | The desktop app or the server |
| Lock file `<company>.bookscraft.lock` | pid, host, process kind, start time (diagnostics only) | Next to the company file | Held with `std::fs::File::try_lock` |
| Backups `*.bookscraft.bak-<timestamp>` | Consistent copies made with the SQLite online backup API: on request, before every migration and import, and daily on the desktop (`auto` copies; only the 7 newest automatic copies per company are kept, other copies are never removed) | `<data_dir>/backups/` by default | Written by the owning process |

`<data_dir>` is the per-user application data directory that `directories::ProjectDirs` computes for qualifier `org`, organization `BooksCraft` and application `BooksCraft`: typically `$XDG_DATA_HOME/bookscraft` on Linux, `%APPDATA%\BooksCraft\BooksCraft\data` on Windows and `~/Library/Application Support/org.BooksCraft.BooksCraft` on macOS. Only the `platform` crate resolves it; nothing else hard-codes a path.

Open sequence (store crate):

1. Take the lock. On failure: `store.company_locked`, with the holder's details from the lock file.
2. Open with `PRAGMA journal_mode = WAL`, `synchronous = FULL`, `foreign_keys = ON`, `busy_timeout = 5000`, `trusted_schema = OFF`.
3. Read `schema_migrations`. If the file has a version newer than the binary knows: `store.file_too_new`, refuse to open.
4. If migrations are pending: back up, then apply them in one transaction each.
5. Run `verify` in quick mode (last 1,000 audit events).

Company files must be on a local disk; WAL does not work on network filesystems. The UI warns when the path looks remote.

Concurrency inside the owning process: one write connection, with every write transaction starting `BEGIN IMMEDIATE`, plus a small read pool (WAL readers). A write transaction never commits while a `journal_entry` is still `open`: the store checks this before `COMMIT` and rolls back with `ledger.entry_left_open`.

Schema evolution: migrations are forward-only, embedded in the binary and numbered `NNNN_<slug>.sql`; only a Weave adds one (CCR process, [OWNERSHIP.md](../coordination/OWNERSHIP.md)). `docs/architecture/schema.sql` always equals the cumulative schema. Store test `schema_matches_spec` builds one database from all migrations and one from `schema.sql`, then compares their normalized `sqlite_schema` rows.

### 4.2 Revisions

A document's `revision` is 0 while it is a draft. It becomes 1 when first posted and increments on every repost. Its lines, tax lines and dimension rows are stored per revision. Rows at revision ≥ 1 are immutable (triggers `document_line_snapshot_*`). New rows can only be written at a revision greater than the document's current one. Reports and services read the current revision through `current_document_line`.

### 4.3 Write path: post, repost, void

Every posting operation is one `BEGIN IMMEDIATE` transaction in this order. The store crate exposes it as `store::ledger::post_revision` and `store::ledger::void_document`.

| Step | Post (revision 0 → 1) | Repost (n → n+1) | Void (n) |
|---|---|---|---|
| 1 | Load the document, verify `version` (optimistic concurrency) | same | same |
| 2 | Copy revision 0 lines, tax lines and dimensions to revision 1 | Write revision n+1 lines, tax lines and dimensions | — |
| 3 | — | Insert reversal entry of `E_n` (open), its postings and dimensions, the lock override if needed, then finalize | same as repost |
| 4 | Insert entry `E_1` (open), postings and dimensions, the override if needed, then finalize | Insert `E_{n+1}`, finalize | — |
| 5 | Insert settlements at revision 1 | Insert settlements at revision n+1 | — (its own settlements become inactive) |
| 6 | Update document: `status = posted`, `revision = 1`, `version + 1` | Update header with `revision = n+1`, `version + 1` | `status = voided`, `voided_at`, `void_reason` |
| 7 | Delete revision 0 rows | — | — |
| 8 | Append clearing events for changed money lines (LEDGER_SPEC §11) | same | same |
| 9 | Append audit event(s), recording each new entry's `content_hash` and the revision's `settlements_hash` (LEDGER_SPEC §10) | same | same |
| 10 | Check that no entry is left `open` and that an audit event was appended, then `COMMIT` | same | same |

The reconciled-line rule, the settlement bounds, the deposit rule and the agent rule (I-10) are checked by the calling service before step 2 and re-checked by storage where possible.

## 5. Enforcement map

| Rule (invariant) | Type level | Storage level | Error code |
|---|---|---|---|
| Entry balances (I-3) | `ledger::BalancedEntry::new` | `journal_entry_finalize` | `ledger.unbalanced`, `ledger.unbalanced_currency`, `ledger.too_few_lines` |
| Postings append-only (I-3) | no mutating API in `store` | `posting_no_update`, `posting_final_no_delete`, `posting_insert_requires_open_entry` | `ledger.posting_immutable`, `ledger.entry_not_open` |
